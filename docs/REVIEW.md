## どういうソフトか

CANVideoEmulatorは、車両の挙動を生成する物理シミュレーターではなく、**記録済み動画とCANを同じ時間軸で再生するベンチ用エミュレーター**です。Windowsだけで動画を確認でき、PCAN-USBを有効にすると選択バスの実記録フレームを外部へ送ります。

Python Builderが、raw_log.bz2を読み、各CANバスを20バイト固定長レコードへ分離し、HEVCをH.264 MP4へ変換します。映像とCANの開始時刻差、信号定義、検証結果をシナリオに保存します。プレーヤーの共通時計はStopwatchベースで、CANのシークには二分探索を使います。動画はWPF MediaElementに任せ、位置ずれが許容値を超えると補正します。

設計上の長所は、UI・送信・再生状態・変換が別プロジェクトに分かれ、実機のないテストでも時計、CANスケジューラー、再生遷移、DBCデコードを検証できる点です。生データの取得と変換を再生環境から分離しているため、展示PCへPythonやFFmpegを配布する必要もありません。

Androidは補助の受信表示プロジェクトです。現時点ではデモ用ファイル入力とデコーダーはありますが、実機向けCanSourceの生成は未実装です。したがって、このリポジトリだけでPCANからAndroidまでの実機経路が完成するわけではありません。

## 今回の変更

- ソリューション・各プロジェクト・名前空間・EXE・インストーラー・表示名をCANVideoEmulatorへ統一。旧ユーザー設定の読み込みは互換性を保持。
- cloneからビルドするsetup.ps1と、公式サンプル取得・DBC準備・変換をまとめるprepare_scenarios.ps1を追加。旧コミット済みEXEを除去し、ソースと実行物の食い違いを避ける運用へ変更。
- Get Scenariosを複数選択・順次取得へ変更。合計容量、再開、キャンセル、取得中の保存先固定を実装。別ボタンで45 MBの公式サンプルを取得可能。
- Windowsで使えないパイプ文字を置換するZIP展開処理を追加。展開パスが出力先を逸脱するアーカイブを拒否。
- CRFと最大動画幅を指定できるようにし、簡易セットアップではCRF 28・最大幅1280を使用。タイムスタンプとCANペイロードは圧縮設定の影響を受けない。
- シナリオ追加時のプレイリストは保存先の全パッケージから再生成。別チャンクを追加したときに既存分が一覧から落ちる問題を修正。
- PCANの手動Refreshと自動監視の切断処理を統一。送信とチャンネル解放を同じロックで保護。USB検出と送信有効化を分け、再接続時は明示操作で再開。
- UIによるハードウェア状態照会を15 Hzから約4 Hzへ抑制し、チャンネルリストが変わらないときは再生成しない。
- BusLight／中断のテスト成功判定を修正。BusHeavy等の悪化も通知し、BUS OFF時は再生を一時停止。デモで物理到達を試験できないことを表示。
- 右側の間隔を縮め、設定を横並びに配置。シナリオ一覧と詳細テストを折りたたみ可能に変更。
- 初回セットアップを4画面に分割し、約200 msのアニメーションと固定ナビゲーションを追加。完了ダイアログの終了時にアプリまで終了しないよう、WPFの起動処理を修正。完了後にメイン画面を開き、セットアップスクリプトも既定でEXEを起動。
- CAN出力テストとレポートを受信機に依存しない文言へ統一し、シナリオ内のDBC／signals.jsonと既存Androidデコーダーの利用方法をCAN定義ガイドへ追加。

実ディレクトリの改名は、この作業環境がフォルダーを使用中のため失敗しました。新名フォルダーへ中身を移す代替操作も自動承認レビューで拒否され、理由の詳細は返されませんでした。現在の実パスはPCANUSBDemoのままです。READMEに、アプリを終了した後のrename_workspace.ps1の実行方法を記載しています。Gitのoriginは既にCANVideoEmulatorです。

## 今後の改善優先順位

### 1. 動画と物理CANの同期を測定して仕様化する

「同じタイミング」が、50 ms以内なのか250 ms以内なのかを先に決める必要があります。現行の動画補正は250 ms閾値・2秒クールダウンで、フレーム精度の同期を保証しません。また、CANスケジューラーは50 ms以上遅れた場合に送信基準時刻を再設定するため、過負荷後に共通時計からのずれを残す可能性があります。

受信CANのハードウェアタイムスタンプと表示フレーム時刻を同時記録し、長時間・CPU高負荷・シーク・ループ時の誤差分布を測定します。その結果をもとに、遅延時に追いつく／フレームを落とす／両方を一時停止する方針を統一すべきです。ジッター表示は現在API呼び出し時刻を基準とし、線上の送信時刻そのものではありません。

### 2. PCAN出力の実機試験を完成させる

PCANのGetStatusが正常でも、物理CANの送信完了は確定できません。独立した受信機で受信数と時刻を測定し、WindowsのAPI受付数と同じ期間で比較します。USB抜去、CAN側断線、電源断、速度不一致、復帰を試験項目に含めます。受信後の転送・表示方式は、本アプリの仕様から分離します。

CAN送信キューの残量や実送信完了を取り込めれば、Pause/Stop後の排出遅延も説明できます。現在の停止は新しいAPI Writeを止める動作で、既にキューへ入ったフレームが同時に消える保証はありません。

### 3. 任意の少数区間を小容量で取得・変換する

今回の45 MBサンプルは初回確認に有効ですが、任意の区間を選ぶ機能ではありません。大きなZIPは依然チャンク全体をダウンロードします。HTTP RangeによるZIP中央ディレクトリと選択エントリーの取得を検討するか、選定済みの小容量Scenario PackageをRelease配布すると、展示PCのセットアップがさらに簡単になります。

取得→全区間変換→一覧更新は画面に統合済みです。次の段階では変換前の区間選定と、空き容量・変換後容量のより正確な見積もりを追加します。現在はPython／FFmpegが必要で、進捗とキャンセルを表示します。

### 4. 取得の整合性と再現性を強める

ダウンロードはサイズとContent-Rangeを検証していますが、暗号学的チェックサム検証は未実装です。SHA-256、ETag、取得元リビジョンを保存すると、同容量の破損・更新されたファイルへの誤再開を検出できます。サンプルとDBCは固定コミットですが、Pythonライブラリーもロックファイル化すると別PCでの再現性が上がります。

Scenario Builderは出力先へ直接書くため、変換中断時に部分的なシナリオが残る可能性があります。一時ディレクトリで変換・検証し、成功時に一括確定する方式が次の改善候補です。

### 5. 車種プロファイルと自動検証を拡張する

標準buildではRAV4とCivicのプロファイルを走行ルートから自動選択します。今後はCivicの複数区間・追加信号を照合し、analyze/build-selected側の車種別設定も統合します。

CIでWindows・Python・Androidデコーダーを継続検証し、Release EXE／セットアップ資材を自動生成する運用が有効です。ハードウェア試験はCIのソフトウェアテストと別のゲートにします。

## 今回確認できた範囲

公式サンプルの必要データ取得→固定DBC生成→動画/CAN変換→パッケージ検証を実行しました。既存サンプルの24,801,825バイトの動画に対し、コンパクト動画は9,226,954バイト、生成パッケージ全体は12,186,599バイトでした。バス0・1のcanbinは、従来パッケージとSHA-256が一致しました。

セットアップスクリプトによる自己完結EXEのビルドと、WPF画面の通常幅・最小幅での描画を確認しました。UI検査では、複数チャンク選択と起動時に送信が有効にならないことも確認しています。.NET SDKは既存のインストールを使用したため、SDK自動インストール分岐と、別の物理PC上での導入は未検証です。

USBチャンネルの検出は確認できましたが、今回、実CAN送信・ケーブルの抜き差し・Androidへの到達・長時間の物理同期は実機検証していません。接続状態の回帰テストは模擬した検出結果を使っています。

最終結果：Windows/xUnit 145件、Python/pytest 68件が成功しました。Androidのコード変更はなく、今回のAndroidテスト／APKビルドは行っていません。

初回セットアップの追加確認では、独立したテスト用設定で4画面のNext/Back、設定保存、完了後のメイン画面表示、次回起動時のセットアップ省略を実行しました。起動時にCAN出力がオフであることも確認しています。
